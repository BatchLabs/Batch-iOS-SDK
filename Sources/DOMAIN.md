# Batch iOS SDK — Domain and wire contracts

The product and backend knowledge you cannot infer from the code. Read this before renaming anything that travels over the network. Paths are relative to `sdk/Batch/` unless they start with `sdk/`.

## 1. Vocabulary

| Term | What it is | Where it lives |
|---|---|---|
| **API key** | Per-app key the integrator passes to `BatchSDK.startWithAPIKey:`. Ends up in every webservice URL. | `BatchCore.h`; internally `BAConfiguration.developperKey` (sic) |
| **Project key** | **Server-issued**, not caller-supplied. Arrives as `project_key` in the attributes and attributes-check responses, persisted under `app.project.key`. | `BAWSResponseAttributesCheck`, `BAWSResponseAttributes`, `Defined.h` |
| **Installation ID** | Per-install identifier generated by Batch. Wire shortname `di`, stored as `app.install.id`. | `BatchUser.h`, `BATSystemParameter.swift`, `Defined.h` |
| **Custom ID** | The integrator's own user identifier, set through `BatchProfile.identify:`. Wire shortname `cus`, stored as `app.id.custom`. Max 1024 chars, and a blocklist rejects `undefined`, `null`, `nil`, `(null)`, `[object object]`, `true`, `false`, `nan`, `infinity`, `-infinity`. | `BatchProfile.h`, `BATProfileDataValidators` |
| **MEP** | Mobile Engagement Platform — the previous backend generation. Data is **install-scoped**. | `CHANGELOG.md`, `BAInstallDataEditor` |
| **CEP** | Customer Engagement Platform — the current generation. Data is **profile-scoped**, i.e. shared across a user's installs. | `CHANGELOG.md`, `BatchProfile` |
| **Install data vs profile data** | `BatchUser`/`BAInstallDataEditor` writes install data (MEP); `BatchProfile`/`BATProfileEditor` writes profile data (CEP) and mirrors into install data for compatibility. | `ARCHITECTURE.md`, "Two generations, side by side" |
| **Local campaign** | An in-app campaign stored on device and evaluated locally. The code says "local campaign" (`Modules/Local Campaigns/`, `BALocalCampaignsCenter`); the public product name in the headers is "In-App Campaign". | `BatchMessagingModels.h`, `BatchCore.h` |
| **Mobile landing** | In-app content attached to a push. Delivered by `BAMessagingCenter` observing `BatchPushOpenedNotification`. | `BAPushCenter`, `BAMessagingCenter` |
| **JIT** | Just-in-time server-side eligibility check for a campaign: 1-second timeout (`LOCAL_CAMPAIGNS_JIT_TIMEOUT`), 60-second default retry-after (`DEFAULT_RETRY_AFTER`), body of `ids`, `campaigns`, `views` and — for MEP only — `attributes`. | `BALocalCampaignsJITService.requestBodyDictionary` |
| **Messaging API level** | Forward-compatibility gate. The SDK declares `BAMessagingAPILevel` in `Versions.h`; a message declaring a higher level is dropped, not degraded. | `Versions.h`, `BAMSGPayloadParser` |

Careful: `BALocalCampaignsVersion.h` expands MEP as "Marketing Engagement Platform". The user-facing strings — `BAInstallDataEditor`'s validation logs and `CHANGELOG.md` — say "Mobile Engagement Platform". The header is the outlier; do not propagate it.

## 2. Payload discriminators

- Push payloads nest everything under the `com.batch` key.
- **`ld` is a MEP message** (a plain JSON dictionary). **`ld2` is a CEP message**: a *string*, Base91J-decoded (`BATBase91J`), gunzipped (`BATGZIP`), then parsed as JSON. Both branches live in `BatchPushMessage.initWithPayload:` (`BatchMessaging.m`), and the resulting `isCEPMessage` flag drives the whole renderer choice.
  Consequence for fixtures: a CEP payload written as a nested dictionary silently falls through to the MEP branch and yields `nil`. It has to be the encoded string.
- Local campaign output types: `LANDING` (MEP) and `LANDING_CEP`, compared in `BALocalCampaignsParser`. The campaign list also carries a `campaigns_version` field valued `MEP` or `CEP` (`BALocalCampaignsVersion.h`).
- Minimum-level keys differ per generation: `minapi` for MEP, `minMLvl` for CEP, both compared against `BAMessagingAPILevel`.

## 3. Wire contracts — do not rename

These look like ordinary internals. They are the protocol. Renaming any of them breaks encoding, decoding, or backend targeting.

**This is an index of vocabularies, not an inventory of strings.** An inventory of literals cannot be kept complete and goes stale on the next commit; successive review rounds each found another vocabulary missing from the list this section used to be. So every **row of the index** names the file and the symbol that *owns* a vocabulary, what the vocabulary is for, which side writes it, and what a rename costs. Where a row prints a literal at all it is a structural one — the single container key or event name the whole vocabulary hangs off, or the name of the `#define` block it lives in — and never a list of that vocabulary's members. For the members, open the symbol and read them off the source.

The **subsections below the index do print members**, and each has its own reason. "Literals that are the trap" prints only the strings where opening the owning symbol is not enough: a wire word that differs from the Swift or Objective-C name it builds, a composed name, a deliberately misleading symbol, a spelling that means two unrelated things, an entry point whose counterpart holds a hard-coded copy. "Private tracker event names", "Server-authored actions" and "Request headers" print whole vocabularies, because those three have no single symbol to point at — the event names are bare literals at their call sites; the pairing of an action identifier to its argument keys exists nowhere in one place (`BAActionsCenter.init` names every identifier, but each action's block reads its own keys, two of them from `BAUserDataBuiltinActions` and `BAUserEventBuiltinActions`); and the header set is spread over `BAConnection`, four `requestHeaders` overrides, `BATWebserviceHMAC` and two webview controllers. Read those three as "at least this, then re-derive from the owners named beside them", never as complete. "CEP enum vocabularies" is the opposite case: there the file name is the index, and the prose records only what reading the file does not tell you.

To answer "is the string I am about to rename part of the protocol?": find the vocabulary it belongs to, open the symbol named beside it, and read the current set off the source. Do not expect the string to appear in the index.

Some of these vocabularies have a contract test that fails on a rename and some do not, and the split is not where you would guess — it is patchy *inside* a single vocabulary, not just between them. The local campaign payload keys are a fair sample: the literal `"persist"` appears in fixtures in `localCampaignsCenterTests.m` and in no fixture in `BALocalCampaignsParserTests.swift`, and `requireJIT` — whose fallback in `BALocalCampaignsParser` is `YES` for CEP and `NO` for MEP, so a rename silently changes which campaigns need a server round-trip before they can display — appears in no test at all. Same story for the built-in actions: `builtinActionsTest.m` and `groupActionTest.swift` between them cover a subset of what `BAActionsCenter.init` registers, and `batch.rating`, `batch.refresh_lc` and the permission actions are not in that subset. So: before renaming any literal reachable from this section, grep the exact string across `sdk/batchTests/` and decide from what comes back. A green suite is not evidence here.

### Literals that are the trap

The discriminators and spellings below are the ones where reading the symbol is not enough, because the wire word and the code word disagree or because one string means two things.

- **The wire word is not the type name.** MEP `kind` `universal` builds `BAMSGMessageInterstitial`, by design. `InAppComponent.text` decodes into `InAppLabel`. Neither mismatch is a bug to tidy up.
- **`InAppAnyTypedComponent` overrides its own `CodingKeys`.** It hand-writes `init(from:)` and `encode(to:)` around a single-value container, so its declared `CodingKeys.component` is never consulted and its `component` property has no wire name at all. A `CodingKeys` is therefore not what establishes the mapping.
- **`InAppWidthType` / `InAppHeightType` are not `Codable`.** The models carry `width` / `height` as plain strings; the builders parse them through `init?(stringValue:)`. The two vocabularies are **not** interchangeable: width accepts `autoKey` (`auto`) and `percentKey` (`%`) only, height accepts `autoKey`, `fillKey` (`fill`) and `fixedKey` (`px`). A height is `"120px"`, a width `"50%"`; a `"fill"` width parses to `nil`. Changing a suffix is a wire break no type checker will catch.
- **The JIT endpoint short names are composed.** `Defined.h` concatenates the in-app short name, the JIT short name and the generation short name at preprocessor level into `inapp_jit_mep` and `inapp_jit_cep`. Renaming any part silently renames an endpoint, and grepping either full string finds nothing.
- **`x` means something different in each suffix vocabulary.** In `BATProfileAttributeOperationType` the `x` raw value never reaches the wire — `delete` has a deliberately empty `keySuffix`, so a CEP deletion goes out as the bare attribute name with an `NSNull` value. Do not "fix" that by emitting it. In `BAUserAttribute.stringForType:` `x` is the `default:` branch and `BAUserAttributeTypeDeleted` is a real enum case that falls into it, so a MEP deleted attribute *does* serialise with the `x` suffix. In `BATTypedEventAttribute.typeSuffix` it is a `default:` nothing reaches: `BAEventAttributeType` is an `NS_CLOSED_ENUM` and every case is handled above it. Same letter, three contracts.
- **The three suffix vocabularies are not one vocabulary.** `BATTypedEventAttribute.typeSuffix` carries a suffix for plain objects that neither of the other two has, and returns the *same* suffix for string arrays and object arrays. `BAUserAttribute.stringForType:` has no array or object case at all. Do not refactor them together on the assumption they agree.
- **`ts` is three unrelated contracts.** The query envelope timestamp is inbound and read by `BAResponseHelper.checkResponse:` out of the response body's `header` block — a JSON key, not an HTTP header; `BAWSQueryTracking.objectToSend` independently writes an event-level `ts` as a hard-coded literal, outbound, from the event's tick; `BALocalCampaignsParser.parseDate:error:` reads a third `ts` as a campaign date. Three different owners, one string — and that is only the ones reachable from the vocabularies indexed above.
- **`t` is a key, one of its own values, and an argument name in three actions.** `BatchInboxNotificationContent.parseSource` reads the source discriminator under the key `t`, and one of the values it compares against is also `t`. `Defined.h` uses `t` as the push webservice short name and, separately, as the push type key. `batch.clipboard` takes its text under `t`, `batch.user.tag` its tag, `batch.user.event` its tag array. Nothing links them.
- **`l` likewise.** It is the deeplink URL in the push payload and in `batch.deeplink`'s arguments, the label in `batch.user.event`'s arguments, and the CTA label in `BAMSGPayloadParser.parseCTA:`.
- **Other cross-vocabulary collisions** worth checking before a global replace: `status` is a query envelope key and a field of the notification-authorization block inside the same body; `body` is a query envelope key and the MEP message text; `views` is a key in the local campaigns query, in the JIT body and in a time-based capping, with `count` nested under the first two; `session` appears in the tracked event dictionary and in the campaign cappings; `tags`, `attributes` and `type` each appear in more than one of the vocabularies above. Scope every rename to one owning symbol.
- **The push container key is both a macro and a bare literal.** `Defined.h` declares it as `kWebserviceKeyPushBatchData`, and the push module and the event-dispatcher payloads read it through that macro — but `BatchPushMessage.initWithPayload:` in `BatchMessaging.m` and `BatchInboxNotificationContent`'s `parseSource` / `parseAttachment` in `BatchInbox.m` spell `com.batch` out by hand. Renaming the macro compiles and leaves those sites reading the old key. Grep the string, not the symbol.
- **MEP layout keys are terse and misleading.** `parseUniversalMessage:withBaseObject:` fills heading, title and subtitle from `h1`, `h2` and `h3`, the hero description from `hdesc`, and the CSS from `style`. `parseBaseBannerMessage:intoObject:` reads a CTA direction whose only accepted values are `h` and `v` — anything else is ignored rather than rejected. Read the method, not the property names.
- **`serializedName` is not a serialisation of the short name.** It is an independent second mapping on the same enum case; see the index rows.
- **The install attribute name on the wire is not the stored name.** `BAUserAttribute.serverJsonRepresentationForAttributes:` strips the first two characters of every key before appending the type suffix, because `BAUserSQLiteDatasource` prefixes stored keys with `n.` or `c.` to separate native from custom. Those prefixes are storage, not protocol; the stripping is what makes them so.
- **The webview bridge has three spellings the page holds its own copy of.** The script message handler is registered under the name `batchBridge` (`BAMSGWebviewViewController.webViewConfiguration`, `InAppWebviewViewController.setupWebviewSettings()`), so the page reaches the SDK as `window.webkit.messageHandlers.batchBridge`; the pre-iOS-14 handler evals `window.batchInAppSDK.__onWebkitCallback` back into the page to deliver a result. Renaming any of the three changes a symbol that lives in JavaScript outside this repository. And `BATWebviewJavascriptBridge.resultProviderForMethod:arguments:` dispatches on `[method lowercaseString]` against all-lowercase literals, so a bridge method name is case-insensitive on the wire while the argument keys its implementation reads are matched exactly.
- **Two action identifiers travel in both directions**, and `$label` / `$tags` travel the reverse way from everything else in their section — both covered under "Server-authored actions".
- **One header escapes the signature it computes** — covered under "Request headers".

### Private tracker event names

`BATInternalEvent` covers only the profile and native-data events. Everything else reaches `BATrackerCenter.trackPrivateEvent:parameters:` (or `BAEvent.eventWithName:`) as a bare string literal at the call site, so there is no single file to read. As of this writing, at least: `_START` (`BACoreCenter`), `_OPEN_PUSH` / `_PUSH_ACTION` / `_PUSH_REGISTER_FAIL` (`BAPushCenter`), `_LC_VIEW` (`BALocalCampaignsCenter`), `_MESSAGING` (`BAMESSAGING_EVENT_NAME` in `BAMessagingCenter.m`), `_INBOX_MARK_READ` / `_INBOX_MARK_ALL_READ` / `_INBOX_MARK_DELETED` (`BAInbox`), `_INSTALL_DATA_CHANGED` (`BAUserDataManager`), `_OPTIN` / `_OPTOUT` / `_OPTOUT_WIPE_DATA` (`BAOptOut`), `_NOTIF_STATUS_CHANGE` (`BANotificationAuthorization`), `_LOCATION_CHANGED` (`BATrackerCenter`), `_FIND_MY_INSTALLATION` (`BADBGFindMyInstallationHelper`). Re-derive the current set by grepping both `trackPrivateEvent` and `eventWithName:` across `sdk/Batch/` — the opt-out events go through the second, not the first, so the obvious single grep under-reports.

The parameter dictionary is as frozen as the event name, and it is assembled at the call site too. `_LC_VIEW` is built in one place, `BALocalCampaignsCenter.didPerformCampaignOutputWithIdentifier:eventData:`. `_MESSAGING` is built in `BAMessagingCenter.baseEventParametersForMessage:type:` and then extended by the per-path `trackGenericEvent:type:`, both `trackCTAClickEvent…` overloads, `trackCloseError:cause:` and `trackWebViewClickEvent:action:analyticsIdentifier:` — and `messageGlobalTapActionTriggered:action:`, which skips the specialised helpers but still starts from that same base dictionary and adds its `action` key inline — so grepping the helper names misses it. Read those methods rather than any list, because `_MESSAGING` has no fixed key set: some keys are written only when the source message carries them, and the webview-click path writes the action identifier under `action` for a CEP message but under `actionName` for a MEP one — two wire names for one value, chosen at runtime by `isCEPMessage`.

One name in this family emits nothing. `Defined.h` declares `kParametersReadReceiptEventName` as `_PUSH_RECEIVED`, and `BAPushPayload.requiresReadReceipt` reads the payload's `r` flag; neither the macro nor that method has a caller anywhere in this repository, and the notification service extension lives in a separate repository. Treat both as dormant declarations — grepping `_PUSH_RECEIVED` to find out how read receipts are sent here leads nowhere.

### CEP enum vocabularies

Property names under `Objects/` are covered by the index above; these are the *values*, and they are just as frozen. Each enum lives in its own file, so the file name is the index — open the file for the current set. What follows is only what reading the file does not tell you.

- `InAppComponent` (`Objects/InAppComponent.swift`) is the `type` discriminator `InAppAnyTypedComponent.init(from:)` switches on; an unknown value rejects the **whole** message rather than skipping a component. Trap: `text` decodes into `InAppLabel`, so the wire word and the Swift type do not match.
- `InAppFormat` (`Objects/InAppFormat.swift`) selects the view controller. `InAppCTAType` (`CTA/InAppCTAType.swift`) goes the other way — outbound: `InAppAnalyticWrapper` sends its `rawValue` as the `ctaType` parameter of the `_MESSAGING` event.
- These vocabularies **overlap without being related**, and the MEP `kind` discriminator overlaps them too: `webview` is a value of `InAppComponent`, of `InAppFormat`, of `InAppCTAType` and of `kind`; `image` of `InAppComponent`, `InAppCTAType` and `kind`; `button` of `InAppComponent` and `InAppCTAType`; `modal` of `InAppFormat` and `kind`. A rename is never global — check each owner separately.
- `InAppVerticalAlignment` (`Types/`) is reused for the message `position`, so its values answer to two different keys.
- `InAppAspectRatio` and `InAppHorizontalAlignment` (`Types/`), `InAppFontDecoration` (`Font/`) — read the files.
- `InAppWidthType` and `InAppHeightType` (`Types/`) are the exception: they are not `Codable` at all, and the literals they parse are listed among the traps above.

### Server-authored actions

`kBAActionsReservedIdentifierPrefix` is `batch.` and `kBAActionGroupName` is `batch.group` (`BAActionsCenter.m`; the comment there requires the two to move together). The prefix is also the public guard: `registerAction:` and `publicPerformAction:withArguments:` refuse any identifier starting with it, so renaming it changes what integrators are allowed to register.

The identifiers registered in `BAActionsCenter.init` and the compact argument keys their blocks read are mostly **written by the backend** — the dashboard puts them in the campaign payload and the SDK matches them verbatim, lowercased. Two of them travel in both directions: the webview controllers of both generations (`BAMSGWebviewViewController`, `InAppWebviewViewController`) emit `batch.dismiss` and `batch.deeplink` themselves, building the `l` / `li` arguments in code. Renaming those two breaks the SDK's own callers as well as the wire.

- `batch.deeplink` — `l` (URL), `li` (open in-app, boolean)
- `batch.dismiss` — no arguments; also the value `BAMSGAction.isDismissAction` compares against
- `batch.group` — `actions`, an array whose entries are themselves arrays: position 0 is the action identifier, position 1 is its argument dictionary if present, and anything beyond is ignored. `performGroupAction:source:` runs a single-element entry with empty arguments, and skips — never aborts on — an entry that is not an array, is empty, whose identifier is not a string, whose second position is present but not a dictionary, or that names `batch.group` (the recursion check is a case-insensitive compare against `kBAActionGroupName`). Only a non-array `actions` aborts. The ceiling of 10 counts dispatch *attempts*: the counter is incremented after `performAction:withArgs:andSource:` returns, whether or not the identifier resolved to a registered action, so ten unknown identifiers exhaust the budget while a skipped entry does not
- `batch.clipboard` — `t` (text)
- `batch.rating`, `batch.refresh_lc` — no arguments
- `batch.user.tag` (`BAUserDataBuiltinActions.tagEditAction`) — `c` (collection), `t` (tag), `a` valued `add` or `remove`
- `batch.user.event` (`BAUserEventBuiltinActions.trackEventAction`) — `e` (event name), `l` (label), `t` (tag array), `a` (attribute dictionary)
- the permission actions, registered under both an `ios_`-prefixed and a bare spelling: `batch.ios_request_notifications` / `batch.request_notifications`, `batch.ios_redirect_settings` / `batch.redirect_settings`, `batch.ios_smart_reoptin` / `batch.smart_reoptin`, `batch.ios_tracking_consent` / `batch.tracking_consent`. Each pair runs the same block, and `BAActionsCenter` names the bare variants `…ActionCEP`. Both are live registrations — deleting either spelling stops whichever generation emits it

`$label` and `$tags`, written by `BAUserEventBuiltinActions.performTrackEvent:`, go the other way: the SDK invents them and the backend reads them. Frozen all the same.

Re-derive the list from `BAActionsCenter.init`: every built-in goes through `registerInternalAction:` there, including the ones it pulls from `BAUserDataBuiltinActions` and `BAUserEventBuiltinActions`.

### Request headers

Four vocabularies live on the same webservice request: ordinary transport headers, the custom-ID authentication header, the cipher headers and the signature headers. All of them feed the signature — except the signature header itself, for the ordering reason below. A fifth set rides on a webview page load instead, and is signed by nothing; it is at the end.

`BAConnection.configureWithMethod:url:body:cryptorFactory:` sets `Accept-Encoding` to `gzip`; `buildRequestWithError:` then sets `Accept` on a GET, and both `Accept` and `Content-Type` on a POST, to whatever `contentTypeString` returns for the connection's content type — currently one value, `application/json`. `BAQueryWebserviceClient` and `BAGETWebserviceClient` each override `requestHeaders` to add `User-Agent` from `BAHTTPHeaders.userAgent`; the base implementation in `BAWebserviceClient` adds nothing. That base is why the inbox *sync* POST carries no `User-Agent` at all while the inbox *fetch* GET does — the sync client descends from `BAWebserviceJsonClient`, the fetch client from `BAGETWebserviceClient`, and neither adds one of its own. These are ordinary transport headers, and renaming one has the obvious HTTP consequence — but it also moves the signature, because of what follows.

`BAInboxFetchWebserviceClient.requestHeaders` and `BAInboxSyncWebserviceClient.requestHeaders` add the one authentication header in the SDK: `X-CustomID-Auth`, carrying the custom-ID authentication key, and only when that key is non-empty. Both overrides spell it out independently, so a rename has to be made twice; and because the header is conditional, the signed header set of an authenticated inbox request differs from an unauthenticated one.

`BAConnection` writes, on the request: `X-Batch-Nonce` (a fresh UUID), `X-Batch-Accept-Cipher` (the cipher version wanted for the response), `X-Batch-Content-Cipher` (POST only, the version of the request body) and, only when downgraded, `X-Batch-Cipher-Downgraded` set to `1`. The server echoes `X-Batch-Content-Cipher` on the response, and `BAWebserviceCryptorFactory.inboundCryptorForData:connection:response:` reads it back through `valueForHTTPHeaderKey:response:` to choose the decryptor. The test is `[@"2" isEqualToString:…]` and **everything else falls back to v1** — a misspelt header name reads as nil, selects the wrong cipher, and the failure surfaces as a corrupt response body rather than a missing header.

`BATWebserviceHMAC.appendToMutableRequest:` then adds `Content-SHA1` (only when there is a body) and `X-Batch-Signature`. Both spellings are returned by `contentHashHeaderKey` and `hmacHeaderKey`.

That makes every header already on the request when the signature is computed load-bearing, not just these: `_filteredHeaders:` excludes nothing (it only drops empty values), and `hmacForMethod:relativeURL:headers:` lists the surviving names — lowercased, sorted case-insensitively — inside the `X-Batch-Signature` value, then `_requestSummaryForMethod:relativeURL:headers:` folds name and value into the signed payload. Adding, removing or renaming any of them changes the signature. The capitalisation of a header *name* does not: it is lowercased on both paths, so do not rely on case to disambiguate. Values are folded in verbatim. `Content-SHA1` is set before the computation, so it is signed like any other header — which also means the signature of a body-carrying request differs in shape from one without.

`X-Batch-Signature` is the exception, purely because of ordering: `appendToMutableRequest:` computes the HMAC over `request.allHTTPHeaderFields` and *then* sets the header, so the signature never covers itself. Renaming `hmacHeaderKey` therefore leaves the computed value byte-identical and simply files it under a name the server does not read — authentication fails with a correct signature in the wrong place, and that is the only rename that leaves the digest untouched. Do not run the inference the other way: a rejected signature is not evidence that the header *set* changed. `_requestSummaryForMethod:relativeURL:headers:` signs each header's value on the same line as its lowercased name, and prefixes the whole thing with the uppercased method and the relative URL, so a different cipher version, a nonce that failed to regenerate, a changed body reaching the summary through `Content-SHA1`, or a URL built differently all move the digest with the header names untouched. Narrow it by diffing the summary, not the header list.

The webview page load is a different request under a different contract. `BAMSGWebviewViewController.loadPageWithCacheEnabled:` (MEP) and `InAppWebviewViewController.loadWebviewWithCacheEnabled(_:)` (CEP) each set `X-Batch-Custom-Region` and `X-Batch-Custom-Language`, from `BatchUser.region` and `BatchUser.language`, and only when the value is non-empty. That request goes to the page the message points at, not to a Batch webservice: it never touches `BAConnection`, so none of the cipher, nonce or signature machinery above applies to it, and whoever reads those headers is whoever serves the webview content. The two generations duplicate the spellings rather than share them, so a rename has to be made twice here too.

Inbound, the SDK reads exactly two response headers: the content-cipher one above, and `Retry-After` — see the response-headers row in the index for what each rename costs.

### Related state machines

Worth knowing before touching the profile pipeline:

- **Attributes-check (`atc`)** answers `OK` / `BUMP` / `RECHECK` / `RESEND`, parsed in `BAWSResponseAttributesCheck` and acted on in `BAUserDataServices`. `BUMP` carries a data version, `RECHECK`/`RESEND` carry a delay.
- The same response carries the **project key**. `BAUserDataServices` fires `BAProfileCenter.onProjectChanged` whenever a non-nil key differs from the stored one, but the migrations inside are guarded on `oldProjectKey == nil` — so they run essentially **once per install, ever**, and are non-idempotent by design.
- `kParametersDNSFallbackFeatureFlag` is `0`: the whole `Modules/Domain/` fallback path is shipped but inert. It is a kill switch, not dead code.

## 4. Limits, and why they differ per generation

The asymmetries below are intentional (`CHANGELOG.md` 3.2.0) — do not "fix" one to match the other:

| Limit | CEP | MEP |
|---|---|---|
| Profile string attribute | 300 chars (`Maximums.stringLength` in `BATProfileEditor.swift`) | 64 chars (`ATTR_STRING_MAX_LENGTH` in `BAInstallDataEditor.m`) |
| Event string attribute | 300 chars (`Maximums.stringLength` in `BATEventAttributesValidator.swift`) | 200 chars, **backend-enforced** |
| Serialized payload | 25 KB (`Maximums.payloadSizeBytes`) — applies to both `BatchProfile.trackEvent` and `BatchProfileEditor.save()`, which reads it back as `BATEventAttributesValidator.maxPayloadSizeBytes` | — |
| Array attribute items | 25 (`stringArrayItems`, `topicPreferencesItems`, `arrayItemsCount`) | — |
| Event label | 200 chars (`Maximums.labelLength`) | — |
| Tag length | 64 chars for event tags (`Maximums.tagLength`) | 64 chars for install tags (`ATTR_STRING_MAX_LENGTH`) |

The MEP 200-character event limit is product knowledge, not code: `CHANGELOG.md` 3.2.0 states that an attribute longer than 200 characters is applied to the CEP only. No SDK constant matches it — do not go looking for one, and do not add one.

Other validated shapes, all in `BATProfileDataValidators`: email max 256 chars, email pattern `^[^@\s]+@[A-z0-9\-\.]+\.[A-z0-9]+$`, phone `^\+[0-9]{1,15}$`, topic preference `^[a-z0-9_]+$`. Attribute and event names are separately gated on `^[a-zA-Z0-9_]{1,30}$` (`BATProfileEditor`, `BATEventAttributesValidator`, `BAProfileCenter`).

## 5. Compatibility policy, as practised

- A minimum OS bump has shipped in a **patch** release: 3.0.1 moved the floor from iOS 13.0 to 15.0 to realign package managers (3.0.2 only restates it). Do not assume semver protects the deployment target.
- A change labelled `Breaking:` shipped in the **minor** release 3.4.0. The "no breaking change without a major bump" rule is aspirational here.
- Deprecation is barely practised. `BatchPushReceivedNotification` in `BatchPush.h` carries an `__attribute__((deprecated))`; the house pattern is outright removal at a major, as 3.0.0 did with the individual messaging close callbacks. Do not promise a deprecation cycle you will not get.
- `api/Batch_objc_api.txt` plus `public-api-check.yml` is **detection, not enforcement** — the workflow never fails on an API diff, it opens a signing PR once a reviewer has approved. See the CI/CD section of the root `AGENTS.md`. Human review is the gate on public API.
- `BAAPILevel` in `Versions.h` is `BASDKVersion` without the dots (`3.4.0` → `340`), and `sdk/Batch/Info.plist` substitutes it into `CFBundleVersion` — so it cannot be left behind on a release, and `README.PRE_RELEASING.md` requires bumping both. The pairing holds across the numbered 3.x releases; the one commit that moved `BASDKVersion` alone was the `3.0.0-alpha` → `3.0.0` finalisation, where `BAAPILevel` was already `300`. Nothing branches on it: `BAPropertiesCenter` reports it as the `lvl` system parameter. `BAMessagingAPILevel` is the real forward-compatibility gate — `BAMSGPayloadParser` rejects a payload whose `minapi` exceeds it, and `BALocalCampaignsManager` drops campaigns outside their `minimumAPILevel`/`maximumAPILevel` — and it is **not** tied to the release: `git log -- sdk/Batch/Versions.h` shows it holding at `30` across the whole 3.0.x line — including the 3.0.4 bump, which carries no tag and whose changelog entry was later folded into 3.1.0 — and then moving once per minor, to `31`, `32`, `33`, `34`. That is all the history establishes; it does not establish a rule, and neither of those minors documents a messaging change: in `CHANGELOG.md`, 3.2.0 carries `Core` and `Profile` notes and 3.3.0 only `Profile`. Go by what the number asserts instead: it tells the backend this SDK renders a newer message format, so raise it when that has become true. Raising it because you are cutting a release makes the SDK accept a payload level its renderer does not implement. `README.PRE_RELEASING.md` is the actual checklist, and says to bump it "only if this release renders a message format the previous one could not".

## 6. Tickets and reviews

- `.issuetracker` maps `sc-(\d+)` to `https://app.shortcut.com/batch/story/$1`. Shortcut is the tracker.
- **Never invent an `sc-` number.** Ask for it.
- Commit subjects are lowercase `prefix: subject`, optionally with a `(scope)`, and with an optional `[sc-NNNNNN]` suffix when a story exists. Two prefix families are in current use side by side — conventional-commit types (`fix`, `feat`, `refactor`, …) and module names (`messaging`, `profile`, `all`, …) — and neither is dominant enough to be the rule. Read `git log` for the area you are touching and match it rather than imposing one.
- `.github/pull_request_template.md` is in French and asks for unit tests, a `CHANGELOG.md` entry, and a Sample app update. It also mentions the internal tools `b47` and `kafkanette`, which are not available from this repository.
- `CODEOWNERS` is a single line, `* @BatchLabs/sdk` — there is no per-area owner to infer.

## 7. Open-source boundary

- The public GitHub repository is **synthesised**, not this one: `public_repo_skeleton/CONTRIBUTING.md` states that development happens privately, only releases are pushed, and pull requests are not accepted. Publication runs from the external `sdk.release-tool` (`README.RELEASING.md`, pipeline `ios-sdk-publish-github-source`).
- Its layout is not this one either. `public_repo_skeleton/BUILDING.md` tells the public reader to open `batch.xcodeproj` at the root and archive `BatchXCFramework` into `Sources/universal`. A path that is correct here is not automatically correct in a public-facing document.
- **No Swift symbol ships as supported API.** Do not read `public` on a Swift type as "supported" — it only means the symbol is reachable from the other targets in this project, and that includes more than the tests: the Sample app imports `Batch` and builds messages out of `InAppImage`, `InAppLabel`, `InAppWidthType` and friends. What ships is narrower than what compiles. The release packaging aggregates (`BatchUniversal`, `BatchXCFramework`) copy the built framework, `cd` into the copy, and run `Tools/Scripts/strip_public_swift_framework.sh` there: it deletes `Headers/Batch-Swift.h` and `Modules/Batch.swiftmodule` and cuts the `Batch.Batch_Private` block out of that framework's `Modules/module.modulemap`, so no Swift interface survives into a released artifact. It never touches the repository — `sdk/Batch/Batch.modulemap` keeps its `//#start-remove-prod` / `//#end-remove-prod` markers, which is precisely why they must be preserved; the script matches on them. An ordinary build of the `Batch` target strips nothing, which is why a Swift API can look fine locally and be absent for integrators. Expose real API through Objective-C headers; see `sdk/AGENTS.md` for the marker convention.
- There is **no in-repo manifest of what gets published**, and nothing marks a file internal-only. What you *can* check before adding a file is its target membership: a non-source file dropped under `sdk/Batch/` is swept into `Batch.framework`'s resources unless it is listed in `membershipExceptions` — see `sdk/AGENTS.md` for the mechanism. Check it; do not assume either answer.
