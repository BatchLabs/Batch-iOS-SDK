# AGENTS.md — `sdk/`

Instructions for the SDK target, its private module, and its unit tests. The repository root `AGENTS.md` still applies; this file narrows it.

## Read first

- `sdk/ARCHITECTURE.md` — startup sequence and `kPluginsList`, dependency injection lifetimes, the notification buses, the persistence map, the webservice chain, the MEP/CEP split, threading sharp edges.
- `sdk/DOMAIN.md` — vocabulary (MEP/CEP, project key vs API key, installation ID vs custom ID), the payload discriminators, the server-dictated constants that must never be renamed, and the real compatibility policy.
- `sdk/Batch/Kernel/Dependency Injection/README.md` — the injectable kinds and when each builds its instance, the silent `nil` on an unregistered key, and the overlay lifetime rules tests depend on.
- `sdk/Batch/Webservices/README.md` — the client hierarchy, how a query is matched to its response, and where encryption and the HMAC are actually applied.

## Adding, renaming, deleting files

- `sdk/Batch` and `sdk/batchTests` are `PBXFileSystemSynchronizedRootGroup`s (`sdk/Batch.xcodeproj`, `objectVersion = 73`). A new `.m` or `.swift` file there compiles with no project edit — never hand-add a `PBXBuildFile`/`PBXFileReference` for one.
- A new internal `.h` under `sdk/Batch/` must be added to the `privateHeaders` list of the `PBXFileSystemSynchronizedBuildFileExceptionSet`. Without it the header never reaches the framework's `PrivateHeaders`, and the `Batch.Batch_Private` module build fails on the import Bridgy generated for it.
- Bridgy does not read the project. It imports every `.h` under `sdk/Batch/` whose **file name** does not match the `ignoredNames` regex in `sdk/bridgy.config.json` — read that config before naming a new header. The regex is what keeps public headers out of `PrivateUmbrellaHeader.h`, and it matches on the name alone: an internal header called `Batch….h` with no `Private` in its name is skipped silently and stays invisible to `import Batch.Batch_Private`.
- A new public `.h` must be added in four places: the `publicHeaders` list, `#import <Batch/…>` in `sdk/Batch/Batch.h`, the matching `explicit module` block in `sdk/Batch/Batch.modulemap`, and `api/Batch_objc_api.txt`. Skipping the modulemap keeps the header invisible to `import Batch.<Submodule>` consumers with no error. A header that only exists to be pulled in by another public header is the exception — `BatchMessagingCloseReason.h` is in `publicHeaders` and reaches consumers through `BatchMessaging.h`, so it needs neither a `Batch.h` import nor its own module block.
- A new non-source file (`.md`, `.json`, …) under `sdk/Batch/` is swept into the framework's Resources phase by the synchronized group. Add it to `membershipExceptions` or it ships inside `Batch.framework`.
- `sdk/OCMock/` has no synchronized group: a new `.m` there must be added to the `Sources` build phase of `OCMock-Batch` by hand.
- `sdk/Batch/PrivateUmbrellaHeader.h` is generated by `Tools/Scripts/generate_private_umbrella_header.sh` (run it from `sdk/`; it resolves `./bridgy.config.json` and `../Tools/Bridgy`) and is rewritten on every build. Never edit it by hand. Bridgy sorts its output, so regenerating on any machine yields a byte-identical file — an unexpected diff means the header set changed, or `sdk/bridgy.config.json` or Bridgy itself did.

## Objective-C and the private module

- Preserve the `Batch.Batch_Private` block and its `//#start-remove-prod` / `//#end-remove-prod` markers in `sdk/Batch/Batch.modulemap`. The release build uses these markers to strip the private module.
- Access internal SDK symbols with `import Batch.Batch_Private` (Swift) or `@import Batch.Batch_Private;` (Objective-C) in tests and sample code.
- Naming is a tendency, not a rule the build enforces, and the prefix does not tell you the language. `Batch*` is public API, `BA*` is internal Objective-C or Swift, `BAWS*` is query/response models, `BADBG*` is the Debug module. `BAT*` covers both Objective-C classes written that way from the start (`BATGZIP`, `BATJsonDictionary`, the `BATWebview*` bridge) and Swift types exported to Objective-C (`BATBase91J`, or an `@objc(BAT…)` alias as on `BATEventTracker`) — and `BATaskDebouncer` and `BATrackerCenter` are `BA` + a `T` word, not `BAT` at all. `BAMSG*` is messaging, not MEP-only messaging UI: `BAMSGPayloadParser` and `BAMSGCEPMessage` both serve CEP. Swift types under `Modules/Messaging/CEP/` mostly take the `InApp` prefix, but internal helpers do not (`WebviewCTAComponent`, the file-private `TypedComponent` in `InAppAnyTypedComponent.swift`). Follow the file you are editing; never infer a type's role from its prefix.
- No Swift symbol ships as supported API. `Tools/Scripts/strip_public_swift_framework.sh` runs at release packaging time — the `BatchUniversal` and `BatchXCFramework` aggregate targets invoke it on each built `Batch.framework` — and deletes `Headers/Batch-Swift.h`, `PrivateHeaders/`, `Modules/Batch.swiftmodule/` and the `Batch.Swift` module block from the modulemap. So `public` in Swift buys reach inside this workspace, where the Sample app does `import Batch` and builds messages out of public Swift types such as `InAppButton`, and nothing at all in a shipped framework. Expose real API through Objective-C headers.
- Register every new injectable in `Kernel/Dependency Injection/Private/BAInjectionRegistrar.m`; an unregistered class or protocol resolves to `nil` silently.

## Swift conventions

- Use line comments (`//`) only: `.swift-format` sets `NoBlockComments`.
- Preserve existing control flow: no `guard`/early-exit rewrites of an existing `if`/`else`. This is a repository convention, not a formatter behaviour — `.swift-format` only disables the `UseEarlyExits` lint rule, it rewrites neither form.
- Default to `internal`, with one formatter-enforced exception: a declaration used only inside its own file must be `private`, because `.swift-format` enables `FileScopedDeclarationPrivacy` with `accessLevel: private`. `public` is for a consumer that reaches the framework from outside — the Sample app, and the test files that use a plain `import Batch` rather than `@testable` (`batchEventAttributesTests.swift` calls `BATEventAttributesSerializer` that way). `@testable import Batch` reaches internal symbols without any `public`, because the project's Debug configuration sets `ENABLE_TESTABILITY` — reach for it before widening a declaration.

## Tests

- Run a single suite or test while iterating: `xcodebuild test -workspace batch.xcworkspace -scheme Batch -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -only-testing:BatchTests/<Suite>/<test>` (the `Makefile` pins that simulator; change it if yours is not installed). The identifier shape follows the test framework, not the language. XCTest — Objective-C and Swift alike — takes the bare method name, and also tolerates a trailing `()`. A Swift Testing test function needs the `()`, and a nested suite needs the nested type chain rather than the `@Suite` display name: `BatchTests/InAppMessageCheckerTests/InAppMessageCheckerText/value()`, never `.../InAppMessageChecker/Text/...`. Get a Swift Testing identifier wrong and xcodebuild runs nothing and still prints `** TEST SUCCEEDED **` — read the `Test run with N tests` line, not the exit status. Adding `-enumerate-tests -test-enumeration-format json -test-enumeration-output-path -` builds the bundle and prints the exact identifiers instead of running them.
- `make test` depends on `clean` and `sdk/sdk.xctestplan` enables ThreadSanitizer and pins language/region/location. Expect minutes, and never assume a slow run is a hang.
- Overlays are process-wide state held one per key, so two suites overlaying the same key must not run concurrently. What actually prevents that today is `sdk/sdk.xctestplan`, which sets `parallelizable: false` on the `BatchTests` target. `@Suite(.serialized)` is narrower than it looks — it serialises a suite's own tests and descendants, not that suite against an unrelated one — so use it to stop a suite racing itself, and do not read it as cross-suite exclusion.
- Keep every `BAOverlayedInjectable` returned by `BAInjection.overlay…` alive until teardown — the registry holds it weakly, so a discarded token dies with the autorelease pool and later calls silently hit the real implementation.
- `removeOverlay(_:)` in `batchTests/XCTest+Injection.swift` does not remove anything: it is a `withExtendedLifetime` call that keeps the overlay alive. The real teardown selector is `BAInjection.unregisterOverlay(_:)`.
- `waitForMainThreadLoop()` and `waitForQueueLoop(queue:)` are `XCTestCase` extensions (`batchTests/XCTest+Threading.swift`), unavailable in Swift Testing suites. There, use `confirmation`/`await` — never a timed sleep.
- Use Swift Testing for new suites, and `XCTestCase` when you need `XCTExpectation`. OCMock is available only in Objective-C XCTest suites: `OCMStub`/`OCMVerify` are C macros with no Swift equivalent, so switching a Swift suite to `XCTestCase` does not unlock it. Swift suites — XCTest and Swift Testing alike — use InstantMock, linked into the `BatchTests` target: subclass `Mock`, adopt the protocol, then `expect()`/`verify()`, and hand it to the SDK with `BAInjection.overlayProtocol(_:returnedInstance:)`. A hand-written double is fine where the mock is trivial.
- Place reusable test doubles under `batchTests/Mocks/` or the module's local test folder; doubles in production code ship in the framework.
